# Codex: AirSIM Relay deployment assistant

This file guides Codex when assisting with `push-relay-worker` deployment. Deployment facts come from the current source, `README.md`, `wrangler.example.toml`, and `package-lock.json`. When the documentation and the source disagree, point out the difference first and do not guess the production configuration.

The current compatibility baseline (2026-10-12) is Apps `v0.9.6`, AVF Agent `v0.4.6` (Debian `0.4.6-1`), and Relay protocol `0.2.1`. The maintainer address is `https://airsim-push.remotepilot.site`. `https://push.remotepilot.site` belongs only to DJOneHub.

## Goals and boundaries

The goal is to deploy AirSIM Relay safely onto the operator's own Cloudflare account, and to let an iPhone/Watch app re-signed with the operator's Apple Developer Team complete automatic registration, PushKit → CallKit incoming calls, and Dashboard authentication.

AirSIM must use a Worker, KV, Durable Objects, Dashboard token, and hostname that are independent of DJOneHub. This project's maintainer uses `https://airsim-push.remotepilot.site`. `https://push.remotepilot.site` continues to belong to DJOneHub. An AirSIM deployment must not take it over or reuse it.

As of 2026-10-08, the maintainer deployment has verified `/healthz`, an anonymous Dashboard `401`, and a `200` with the correct Bearer token. At the time of that check, no AirSIM device was registered. Do not describe infrastructure and authentication readiness as acceptance of real APNs, Agent heartbeats, commands, or cloud PCM.

The following operations require explicit user authorization before they run: creating Cloudflare resources, writing or rotating Secrets, deploying the Worker, binding or migrating a domain, changing DNS, and rolling back a live version. Read-only checks, tests, and `wrangler deploy --dry-run` may run first.

## What the operator must hold

- Cloudflare account/zone permission and the target hostname.
- A new, independent KV namespace. Do not reuse resource IDs from another environment.
- Their own Apple Developer Team, a unique primary Bundle ID, development and distribution signing, and a provisioning profile.
- The APNs Key ID, Team ID, and `AuthKey_<KEY_ID>.p8` that belong to that Team.
- A Dashboard Bearer token generated by a password manager.

Do not ask the user to paste a `.p8`, Dashboard token, Cloudflare API token, device Secret, or APNs token into chat. Have the operator enter them at the local Wrangler prompt or in the CI Secret Store, and report only whether the name was configured successfully.

## Deployment contract that must stay unchanged

- Worker entry: `src/index.mjs`.
- KV binding: `DEVICES`.
- Durable Objects: `MEDIA/CallMediaSession`, `STATUS/AgentStatusRegistry`, `COMMANDS/DeviceCommandSession`.
- Keep these migrations: `v1-call-media`, `v2-agent-status`, `v3-device-commands`. A live change may only append a new tag.
- Plain variables: `APNS_TEAM_ID`, `APNS_KEY_ID`, `ALLOWED_BUNDLE_ID`, `WEBRTC_TRANSPORT_READY`, `WEBRTC_ROLLOUT_PERCENT`.
- Required Worker Secrets: `APNS_P8`, `DASHBOARD_TOKEN`.
- `[secrets].required` declares Secret names only. It does not contain, generate, or upload Secret values.
- `com.example.airsim` is a source-repository placeholder and must not be published. The primary app, Watch app, Live Activity, provisioning profile, Relay allowlist, and APNs topic must use the operator's own consistent identity relationship.
- Debug/development signing corresponds to APNs `sandbox`. Release/TestFlight corresponds to `production`.
- Wrangler deploys infrastructure only. A device self-registers when the signed app calls `POST /v1/devices/register`. Do not keep a static device table or prefill KV by hand.

## Safe operating order

### 1. Read-only checks

```sh
cd push-relay-worker
npm ci
npm test
npm run check
npx wrangler whoami
```

Have the operator confirm the current Cloudflare account. Check whether the target hostname already has DNS, a Custom Domain, or a Worker route. If it does, stop write operations and report ownership and migration risk first.

### 2. Prepare the local configuration

```sh
cp wrangler.example.toml wrangler.toml
npx wrangler kv namespace create DEVICES
```

The second command creates a cloud resource and requires authorization first. Write the returned new namespace ID, the operator's own Apple Team ID and Key ID, primary Bundle ID, and target domain into the Git-ignored `wrangler.toml`. Do not overwrite IDs from another environment.

### 3. Validate the configuration without uploading

```sh
npx wrangler deploy --dry-run --config wrangler.toml
```

Show the operator a redacted Worker name, the last four characters of the KV ID, the DO bindings, the route, the Bundle ID, and the APNs environment. Any remaining `REPLACE_WITH_`, `com.example.airsim`, or wrong hostname must block deployment.

### 4. Inject the required Secrets

Interactive production configuration:

```sh
npx wrangler secret put APNS_P8 --config wrangler.toml
npx wrangler secret put DASHBOARD_TOKEN --config wrangler.toml
npx wrangler secret list --config wrangler.toml
```

`APNS_P8` is a complete multi-line PEM. `DASHBOARD_TOKEN` is AirSIM Dashboard's own random Bearer token, separate from a Cloudflare API token. `secret list` may be used only to confirm names.

Note: `wrangler secret put` creates and immediately deploys a new Worker version, so it is itself a production write. When a first deploy or CI must upload both Secrets together with the code, use a protected temporary file that Git ignores:

```sh
npx wrangler deploy \
  --config wrangler.toml \
  --secrets-file .env.production
```

CI must generate `.env.production` dynamically from the platform Secret Store, destroy it when the job ends, and must not cache it. A gradual release uses `wrangler versions secret put`, then a version deploy. Do not call `secret put` directly.

### 5. Deploy and verify

After the user confirms the dry-run summary and explicitly asks to go live:

```sh
npm run deploy
curl --fail --show-error https://YOUR_RELAY_HOST/healthz
```

Continue verification:

1. An anonymous Dashboard API returns `401`. The correct Bearer token can read a redacted summary.
2. The re-signed app registers successfully, and the Dashboard shows a registration event.
3. A debug device uses sandbox only. Release/TestFlight uses production only.
4. The iPhone VoIP, ordinary APNs, Watch VoIP, and Live Activity topics are each correct.
5. A real PushKit incoming call in the background or on the lock screen reaches CallKit promptly.
6. A wrong device Secret, a cross-device command, an expired call, and unauthenticated media are all rejected.

## Prohibited actions

- Do not read, print, commit, cache, or copy any real Secret.
- Do not write a `.p8` or Dashboard token into `[vars]`, TOML, source, the README, command arguments, or logs.
- Do not sign with the original author's Bundle ID or App ID, or with `com.example.airsim`.
- Do not bind the AirSIM Worker to the hostname that serves DJOneHub, and do not reuse DJOneHub KV or Durable Objects.
- Do not delete or reorder Durable Object migrations, and do not delete KV or Durable Objects in order to "redeploy".
- Do not edit device records by hand to bypass the `device_secret` check.
- Do not claim that CallKit has a separate server certificate. The Relay uses an APNs token key.
- Do not claim that PushKit/CallKit went live successfully when real-device verification is missing.

## Failure and rollback

- `BadDeviceToken`: check sandbox versus production. Do not switch environments blindly.
- `DeviceTokenNotForTopic`: check the primary Bundle ID, the Watch and Live Activity suffixes, the profile, and the APNs topic.
- `InvalidProviderToken`: check that the `.p8`, Key ID, and Team ID belong to the same Team.
- If a Secret or code release fails: keep KV and Durable Objects, and roll back to the previous Worker version. Do not delete migrations.
- On a domain conflict: stop the deployment, keep the existing route, and report the specific bindings that need to be migrated.

The completion report must include test results, the Worker version, hostname, health check, iOS/APNs environment, registration and real push results, the rollback point, and every unverified item. Credentials may be reported only as "configured" or "not configured".
