# AirSIM v0.9.7.1 — Android 10–13 fix, recommended install

Date: 2026-10-14 (Asia/Shanghai). Published from the `VoBLE` branch. **Users on Android 10, 11, 12, and 13 should install this release, and should prefer Standalone.** It fixes startup crashes and VoBLE pairing crashes on older systems, and includes cloud hang-up and voice-jitter improvements. The Linux AVF Agent stays at `v0.4.6`. Relay and the workflow are unchanged, and this is not merged to main.

## Download and upgrade

- `AirSIM-Android-Standalone-0.9.7.1-Android10-13.apk`
- `AirSIM-Android-AVF-0.9.7.1-Android10-13.apk` (for older AVF deployments only)
- `AirSIM-iOS-0.9.7-build81-unsigned.ipa` (main app, Watch, and Live Activity; must be re-signed)
- `SHA256SUMS.txt`

Package name `com.airsim.phonecontrol.standalone`, `versionName=0.9.7.1`, `versionCode=81`, `minSdk=29`, `targetSdk=35`, not debuggable. This is an older-Java-API compatibility fix for Android 10, 11, 12, and 13. It does not forcibly block install on newer systems, and it does not fix crashes by lowering targetSdk or bypassing permissions.

It keeps the original official Android release certificate and can overwrite the official Standalone build directly, preserving pairing, configuration, and local data. Logs do not need to be cleared and the app does not need to be uninstalled. A debug certificate or a third-party re-signed build cannot overwrite it directly. A signature conflict is not a reason to clear data. The AVF build uses a different package name and the two cannot overwrite each other.

## Root cause and fix

Both a Xiaomi Android 12 device and a vivo Android 11 report supplied by the user showed `NoSuchMethodError`. The first site was the home screen reading logs and calling `ByteArrayOutputStream.toString(Charset)`, which does not exist on the older system. Further on-device checks located `Collection.toArray(IntFunction)` in the permission list. This is not a Relay quota, a pairing error, or corrupted user data. Clearing data does not fix it.

The fix covers seven UTF-8/ASCII decodes, four fixed-length stream reads, and two permission-list conversions, across logs, crash reports, Agent/installer HTTP, Standalone Relay/WS, VoWLAN, and the PCM handshake. It uses string construction available on older systems, `DataInputStream.readFully`, and `toArray(new String[0])`, and keeps the original authentication, frame-length, and incomplete-frame rejection behavior.

A new build-artifact method-reference check reproduced the failure on the old implementation, then passed after the fix, and is wired into the shared tests and the official APK build. That check only prevents these known regressions. It is not a complete API lint. A real diagnostic-file UTF-8 read/write test was added so a test cannot pass only because a log stand-in is used.

## Verification limits

Review fixes: replace `StringBuilder.isEmpty`, the URL encode/decode `Charset` overloads, and `InputStream.nullInputStream`. The SMS factory branches on API 31. New AVF background-start options branch on API 34. Mute no longer depends on the OEM `cmd audio`. It uses shell-identity `AudioManager` and read-back checks. Failure is not reported as success. Restore keeps the original mute/volume snapshot for retry.

- Shared Android tests, Standalone integration, diagnostic-file read/write, 47 PCM bridge checks, and the officially signed APK build were run again. Use this release's verification results.
- Redmi M2004J19C (API 31 / Android 12): the fixed package was installed over the existing app with data kept, and it started. The user confirmed VoBLE pairing works. The compatibility branch passed read-only checks of `app_process` and the audio backend. The latest two-ended cloud call user feedback was “no longer reproduces, audio is more stable.” That is not the same as full OEM mute/restore acceptance or acceptance of every network scenario.
- vivo V2111A (API 30 / Android 11): the user's older crash report hit the same log-read root cause. This fixed package has not been retested there yet.
- Android 10, 13, and realme have not completed this round of on-device verification. This release does not claim that every model is free of crashes or that every model supports cellular PCM. The default phone role, Shizuku, Bluetooth permissions, and OEM audio routing still have to be set and verified per device.

## iOS and cloud-call improvements

- iOS is `0.9.7 (81)` (the Apple version number is separate from this Android patch version). The maintainer uploads TestFlight through Xcode with production APNs. A successful upload is not the same as processing finished, external testing available, or review passed.
- “Pair Samsung development phone” is now “Pair Android phone,” with a “Local-mode pairing” switch that controls only the current configuration package. When on, it does not read or write Relay, push, or cloud parameters. When off, it writes through the cloud pairing flow. It does not change the global mode.
- After hang-up, late active/connecting updates, old dial results, and reconnect callbacks for the old call are rejected, so the UI does not reappear or act on the next call by mistake. The same protection covers Watch and Dynamic Island state.
- Cloud PCM on both ends uses bounded adaptive buffering, a 20 ms playback/send cadence, short-gap missing-frame compensation, and discard of stale speech. Android audio capture is decoupled from send and receive, and media can be restarted after reconnect.
- The existing Relay and PCM protocols are unchanged. VoWLAN/VoBLE media implementations were not replaced. Severe weak-network head-of-line blocking on WebSocket/TCP still has limits. See the [design and verification record](../cloud-pcm-resilience.md).
- Before release, 110 iOS tests, the shared Android/Standalone tests, 47 PCM checks, the older Java API reference scan, and NewApi lint were run. A full lint history of permission diagnostics is still not the same as zero warnings. More vendors, Android 10/13, Watch, and long weak-network sessions still need acceptance.

The public IPA **has no Apple signature or provisioning profile, cannot be installed directly, and cannot be uploaded to TestFlight directly**. Use your own Team, Bundle ID, and a complete nested-target signature. The Release does not publish development-device UDIDs. An officially signed APK can overwrite a package with the same certificate and keep data. Uninstalling, clearing logs, or pairing again is not required.
